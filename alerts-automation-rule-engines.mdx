A freezer compressor fails at 3 in the morning. The chart shows it clearly, and nobody is looking at the chart. An alert sends the fact to a person. But an alert that fires every night for no reason is ignored on the night that matters, so most of the work is in choosing the rule. In this lesson you choose rules that people will trust, build a Python alert engine that checks them against live MQTT data, send alerts through five channels, build automation flows with Node-RED, and compare these with the managed alerts on SiliconWit.io. #Alerts #Automation #NodeRED

## Why Alerting Matters

A chart helps only while someone looks at it. An alert system checks each new reading against rules and tells a person when a rule is met.

Sending the message is the easy part. Every alert needs four choices, made before any code is written:

1. **The field.** The one measured value that shows the problem. For a cold room it is the air temperature.
2. **A limit that leaves time to act.** Work back from the damage. Suppose the stock is harmed at 8 °C, the room warms 0.1 °C per minute when the compressor stops, and a technician needs 30 minutes to arrive. In that time the room warms 0.1 × 30 = 3 °C, so the limit must be 8 minus 3 = 5 °C or lower. An alert at 7.5 °C only announces the loss.
3. **How long the condition must last.** A door open for one minute also passes 5 °C. Require the condition to hold for some time, and add that time to the time to act.
4. **Who is told next.** If the first person does not confirm in a set time, the alert goes to a second person. This is called escalation.

The drawing shows the third choice. The short peak does not fire the alert. The long one does, 30 seconds after it passes the limit.

```text
 temperature
     │                        ┌──────────────────
  35 │- - - ┌──┐ - - - - - - -│- - - - - - - - - -  limit
     │      │  │              │
     │──────┘  └──────────────┘
     └─────────────────────────────────────────► time
            short peak:       above the limit for
            no alert          30 s: alert fires
```

One failure passes no limit at all. A device that has lost power sends nothing, so a rule on its readings never fires. Only something outside the device can notice the silence, with a rule of the form "no data for N minutes".

## Alert Types

<InArticleAd />


A limit on one value does not catch every failure. Four types of alert cover most of them.

<CardGrid>
  <Card title="Threshold Alerts" icon="warning">
    The most common type. Fire when a value passes a limit: temperature above 35 C, battery voltage below 3.2 V. The limit can be upper, lower, or both.
  </Card>

  <Card title="Status Alerts" icon="error">
    Fire when a device changes state. The most important one is "device offline": the broker has received no message from the device for 5 minutes. Also: device reconnected, wrong firmware version, unexpected restart (the uptime counter went back to zero).
  </Card>

  <Card title="Rate-of-Change Alerts" icon="rocket">
    Fire when a value changes too fast. A pressure that falls 10 kPa in 30 seconds may mean a burst pipe, although the value is still inside its limits.
  </Card>

  <Card title="Inactivity Alerts" icon="star">
    Fire when expected data stops. The device may still be connected while one of its sensors has stopped: a soil moisture sensor that publishes every 60 seconds has sent nothing for 10 minutes.
  </Card>
</CardGrid>

## Building a Python Alert Engine

<InArticleAd />


The alert engine subscribes to MQTT topics and reads its rules from a JSON file. For each rule it remembers how long the condition has lasted, and it stays quiet for a set time after an alert (the cooldown), so that one long event does not send a message with every reading.

### Architecture Overview

```text
┌─────────────┐     ┌──────────────┐     ┌───────────────┐
│ MQTT Broker │────►│ Alert Engine │────►│ Notifications │

└─────────────┘     │  Rules JSON  │     │ Discord/Slack/│
                    └──────────────┘     │ Telegram      │

```

### Rule Configuration Format

Each rule is a JSON object. It holds the four choices in a form the engine can read, except escalation, which this small engine does not have.

```json title="rules.json"
    }

```

**Rule fields explained:**

| Field | Description |
|-------|-------------|
| `id` | Unique identifier for the rule |
| `topic` | MQTT topic to subscribe to (supports wildcards) |
| `field` | JSON key to extract from the payload (`null` for inactivity) |
| `operator` | Comparison: `>`, `<`, `>=`, `<=`, `==`, `!=`, `rate_below`, `rate_above`, `inactivity` |
| `threshold` | The value to compare against. For `rate_below` and `rate_above` it is the change in value inside `rate_window_seconds` (for example, `-10.0` means a drop of 10 units within the window). For `inactivity` it is the silent time in seconds |
| `sustained_seconds` | How long the condition must persist before firing (0 = instant) |
| `cooldown_seconds` | Minimum time between repeated alerts for the same rule |
| `severity` | `info`, `warning`, `critical` |
| `actions` | List of notification channels to use |

### The Alert Engine

The class below keeps the memory of one rule. For each new reading, `check_condition` and `should_fire` ask three questions in this order:

```text
  ┌────────────────┐
  │ temp > 35 C ?  │──NO──► reset the timer
  └───────┬────────┘
          │ YES
          ▼
  ┌────────────────┐
  │ for 30 s ?     │──NO──► wait for the next reading
  └───────┬────────┘
          │ YES
          ▼
  ┌────────────────┐
  │ in cooldown ?  │──YES─► stay quiet
  └───────┬────────┘
          │ NO
          ▼
    send the alert
```

```python title="alert_engine.py"
import json
import time
import threading
from collections import defaultdict
from datetime import datetime, timezone
import paho.mqtt.client as mqtt

# --- Configuration ---
MQTT_BROKER = "localhost"
MQTT_PORT = 1883
MQTT_USERNAME = "alert-engine"
MQTT_PASSWORD = "secure-password"
RULES_FILE = "rules.json"

# --- Load rules ---
def load_rules(path):
    with open(path, "r") as f:
        data = json.load(f)
    return data["rules"]

# --- State tracking ---
class AlertState:
    """Tracks the state of a single alert rule."""

    def __init__(self, rule):
        self.rule = rule
        self.condition_start = None   # When the condition first became true
        self.last_alert_time = 0      # Timestamp of the last alert sent
        self.last_value = None
        self.last_message_time = 0    # For inactivity tracking
        self.value_history = []       # For rate-of-change tracking

    def update_value(self, value, timestamp):
        """Record a new value and its timestamp."""
        self.last_value = value
        self.last_message_time = timestamp

        # Keep a rolling window for rate-of-change calculations
        window = self.rule.get("rate_window_seconds", 60)
        self.value_history.append((timestamp, value))
        cutoff = timestamp - window
        self.value_history = [
            (t, v) for t, v in self.value_history if t >= cutoff
        ]

    def compute_rate(self):
        """Compute the change in value across the configured window
        (newest value minus the oldest value still inside the window)."""
        if len(self.value_history) < 2:
            return 0.0
        oldest_t, oldest_v = self.value_history[0]
        newest_t, newest_v = self.value_history[-1]
        return newest_v - oldest_v

    def check_condition(self, now):
        """
        Evaluate the rule condition. Returns True if the alert
        should fire, False otherwise.
        """
        rule = self.rule
        op = rule["operator"]

        # --- Inactivity check ---
        if op == "inactivity":
            if self.last_message_time == 0:
                return False  # Never received a message yet
            silence = now - self.last_message_time
            return silence >= rule["threshold"]

        # --- Rate-of-change checks ---
        if op in ("rate_below", "rate_above"):
            rate = self.compute_rate()
            if op == "rate_below":
                triggered = rate < rule["threshold"]
            else:
                triggered = rate > rule["threshold"]
        else:
            # --- Standard threshold checks ---
            if self.last_value is None:
                return False
            v = self.last_value
            t = rule["threshold"]
            if op == ">":
                triggered = v > t
            elif op == "<":
                triggered = v < t
            elif op == ">=":
                triggered = v >= t
            elif op == "<=":
                triggered = v <= t
            elif op == "==":
                triggered = v == t
            elif op == "!=":
                triggered = v != t
            else:
                triggered = False

        # --- Sustained condition check ---
        sustained = rule.get("sustained_seconds", 0)
        if triggered:
            if self.condition_start is None:
                self.condition_start = now
            elapsed = now - self.condition_start
            if elapsed >= sustained:
                return True
            return False
        else:
            # Condition cleared, reset the timer
            self.condition_start = None
            return False

    def should_fire(self, now):
        """
        Returns True if the condition is met AND the cooldown
        period has elapsed since the last alert.
        """
        if not self.check_condition(now):
            return False
        cooldown = self.rule.get("cooldown_seconds", 0)
        if (now - self.last_alert_time) < cooldown:
            return False
        return True

    def mark_fired(self, now):
        """Record that an alert was sent."""
        self.last_alert_time = now
        self.condition_start = None  # Reset sustained timer
```

### Processing MQTT Messages

The second class connects to the broker and passes each message to every rule whose topic matches. A separate thread wakes every 30 seconds to check the inactivity rules, because silence sends no message that could start a check.

```python title="alert_engine.py (continued)"
class AlertEngine:
    """Main engine: subscribes to MQTT, evaluates rules, dispatches alerts."""

    def __init__(self, rules_file):
        self.rules = load_rules(rules_file)
        self.states = {}
        self.notifiers = {}
        self.lock = threading.Lock()

        # Create state objects for each rule
        for rule in self.rules:
            self.states[rule["id"]] = AlertState(rule)

        # Set up MQTT client
        self.client = mqtt.Client(
            mqtt.CallbackAPIVersion.VERSION2,
            client_id="alert-engine",
            protocol=mqtt.MQTTv5
        )
        self.client.username_pw_set(MQTT_USERNAME, MQTT_PASSWORD)
        self.client.on_connect = self._on_connect
        self.client.on_message = self._on_message

    def register_notifier(self, name, notifier_func):
        """Register a notification channel by name."""
        self.notifiers[name] = notifier_func

    def _on_connect(self, client, userdata, flags, reason_code, properties):
        print(f"[{datetime.now().isoformat()}] Connected to broker (rc={reason_code})")
        # Subscribe to all topics referenced by rules
        topics = set(rule["topic"] for rule in self.rules)
        for topic in topics:
            client.subscribe(topic, qos=1)
            print(f"  Subscribed to: {topic}")

    def _on_message(self, client, userdata, msg):
        now = time.time()
        topic = msg.topic

        # Parse JSON payload
        try:
            payload = json.loads(msg.payload.decode("utf-8"))
        except (json.JSONDecodeError, UnicodeDecodeError):
            return

        with self.lock:
            for rule_id, state in self.states.items():
                rule = state.rule

                # Check if this message matches the rule topic
                if not self._topic_matches(rule["topic"], topic):
                    continue

                # Extract the field value
                field = rule.get("field")
                if field and field in payload:
                    # null, text or a missing sensor: skip the reading. An
                    # exception here would end loop_forever and the engine.
                    try:
                        value = float(payload[field])
                    except (TypeError, ValueError):
                        continue
                    state.update_value(value, now)
                elif rule["operator"] == "inactivity":
                    # Any message on this topic resets inactivity
                    state.last_message_time = now
                else:
                    continue

                # Check if the alert should fire
                if state.should_fire(now):
                    self._dispatch(state, now)
                    state.mark_fired(now)

    def _topic_matches(self, pattern, topic):
        """Simple MQTT topic matching with + and # wildcards."""
        pattern_parts = pattern.split("/")
        topic_parts = topic.split("/")

        for i, p in enumerate(pattern_parts):
            if p == "#":
                return True
            if i >= len(topic_parts):
                return False
            if p == "+":
                continue
            if p != topic_parts[i]:
                return False

        return len(pattern_parts) == len(topic_parts)

    def _dispatch(self, state, now):
        """Send notifications through all channels configured for this rule."""
        rule = state.rule
        alert_data = {
            "rule_id": rule["id"],
            "rule_name": rule["name"],
            "severity": rule["severity"],
            "value": state.last_value,
            "threshold": rule["threshold"],
            "operator": rule["operator"],
            "timestamp": datetime.fromtimestamp(
                now, tz=timezone.utc
            ).isoformat(),
        }

        message = (
            f"[{alert_data['severity'].upper()}] "
            f"{alert_data['rule_name']}: "
            f"value={alert_data['value']}, "
            f"threshold={alert_data['operator']}{alert_data['threshold']}"
        )

        print(f"[{alert_data['timestamp']}] ALERT: {message}")

        # Send from a separate thread. This method runs in the MQTT network
        # thread with the lock held: a mail server that takes 30 s would
        # stop every rule and the keepalive with it.
        threading.Thread(
            target=self._notify_all, args=(rule, alert_data, message),
            daemon=True,
        ).start()

    def _notify_all(self, rule, alert_data, message):
        for action in rule.get("actions", []):
            notifier = self.notifiers.get(action)
            if notifier:
                try:
                    notifier(alert_data, message)
                except Exception as e:
                    print(f"  Notifier '{action}' failed: {e}")

    def start(self):
        """Connect to broker and start processing."""
        self.client.connect(MQTT_BROKER, MQTT_PORT, keepalive=60)

        # Start inactivity checker in a background thread
        inactivity_thread = threading.Thread(
            target=self._inactivity_loop, daemon=True
        )
        inactivity_thread.start()

        # Blocking loop
        print("Alert engine running. Press Ctrl+C to stop.")
        self.client.loop_forever()

    def _inactivity_loop(self):
        """Periodically check inactivity rules."""
        while True:
            time.sleep(30)
            now = time.time()
            with self.lock:
                for rule_id, state in self.states.items():
                    if state.rule["operator"] != "inactivity":
                        continue
                    if state.should_fire(now):
                        self._dispatch(state, now)
                        state.mark_fired(now)
```

:::caution[What this engine does not catch]
- A device that was already silent when the engine started. The inactivity rule counts from the first message it sees, so it never reports a device it has never heard.
- Its own failure. The memory of every rule is lost at a restart, and an engine that has stopped sends nothing. Watch the engine from another machine.
- A person who does not answer. There is no escalation here.
:::

### Email via SMTP

```python title="notifiers/email_notifier.py"
import smtplib
from email.mime.text import MIMEText
from email.mime.multipart import MIMEMultipart

# Configuration (use environment variables in production)
SMTP_HOST = "smtp.gmail.com"
SMTP_PORT = 587
SMTP_USER = "alerts@yourdomain.com"
SMTP_PASSWORD = "app-specific-password"
RECIPIENT = "operator@yourdomain.com"

def send_email(alert_data, message):
    """Send an alert email via SMTP."""
    severity = alert_data["severity"].upper()
    subject = f"[IoT {severity}] {alert_data['rule_name']}"

    # Build HTML body
    html = f"""
    <html>
    <body>
      <h2 style="color: {'red' if severity == 'CRITICAL' else 'orange'};">
        {severity}: {alert_data['rule_name']}
      </h2>
      <table>
        <tr><td><b>Rule ID:</b></td><td>{alert_data['rule_id']}</td></tr>
        <tr><td><b>Value:</b></td><td>{alert_data['value']}</td></tr>
        <tr><td><b>Threshold:</b></td>
            <td>{alert_data['operator']}{alert_data['threshold']}</td></tr>
        <tr><td><b>Time:</b></td><td>{alert_data['timestamp']}</td></tr>
      </table>
    </body>
    </html>
    """

    msg = MIMEMultipart("alternative")
    msg["Subject"] = subject
    msg["From"] = SMTP_USER
    msg["To"] = RECIPIENT
    msg.attach(MIMEText(message, "plain"))
    msg.attach(MIMEText(html, "html"))

    with smtplib.SMTP(SMTP_HOST, SMTP_PORT, timeout=15) as server:
        server.starttls()
        server.login(SMTP_USER, SMTP_PASSWORD)
        server.sendmail(SMTP_USER, RECIPIENT, msg.as_string())

    print(f"  Email sent to {RECIPIENT}")
```

### SMS via Twilio

```python title="notifiers/sms_notifier.py"
import requests

# Twilio credentials (use environment variables in production)
TWILIO_ACCOUNT_SID = "ACxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
TWILIO_AUTH_TOKEN = "your_auth_token"
TWILIO_FROM_NUMBER = "+1234567890"
RECIPIENT_NUMBER = "+0987654321"

def send_sms(alert_data, message):
    """Send an SMS alert via the Twilio API."""
    url = (
        f"https://api.twilio.com/2010-04-01/"
        f"Accounts/{TWILIO_ACCOUNT_SID}/Messages.json"
    )

    body = (
        f"IoT Alert [{alert_data['severity'].upper()}]\n"
        f"{alert_data['rule_name']}\n"
        f"Value: {alert_data['value']}\n"
        f"Threshold: {alert_data['operator']}{alert_data['threshold']}"
    )

    resp = requests.post(
        url,
        data={
            "From": TWILIO_FROM_NUMBER,
            "To": RECIPIENT_NUMBER,
            "Body": body,
        },
        auth=(TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN),
        timeout=10,  # never wait for ever on a network call
    )

    if resp.status_code == 201:
        print(f"  SMS sent to {RECIPIENT_NUMBER}")
    else:
        print(f"  SMS failed: {resp.status_code} {resp.text}")
```

```python title="notifiers/discord_notifier.py"
import requests

# Create a webhook in Discord: Server Settings -> Integrations -> Webhooks
DISCORD_WEBHOOK_URL = "https://discord.com/api/webhooks/YOUR_WEBHOOK_ID/YOUR_WEBHOOK_TOKEN"
```

### Telegram Bot

```python title="notifiers/telegram_notifier.py"
import requests

# 1. Message @BotFather on Telegram to create a bot and get a token
# 2. Send a message to your bot, then fetch the chat_id from:
#    https://api.telegram.org/bot<TOKEN>/getUpdates

def send_telegram(alert_data, message):
```

### Testing the Alert Engine

You do not need real sensors to test. Open a second terminal and publish test messages with `mosquitto_pub`:

```bash title="Test: trigger a high temperature alert"
# Publish a temperature above the 35 C threshold
mosquitto_pub -h localhost -u test -P testpass \
  -t "sensors/greenhouse/temperature" \
  -m '{"temperature": 37.5, "humidity": 65.2}'
```

```bash title="Test: sustained condition (run in a loop)"
# Publish every 5 seconds for 60 seconds to trigger sustained alerts
for i in $(seq 1 12); do
  mosquitto_pub -h localhost -u test -P testpass \
    -t "sensors/greenhouse/temperature" \
    -m "{\"temperature\": 38.$(($RANDOM % 10)), \"humidity\": 70.1}"
  sleep 5
done
```

The single message of the first test only starts the 30-second timer. The loop of the second test keeps the value above the limit long enough, and the engine prints the alert and sends the notifications.

**Check it.** Count the alerts, not just their presence. The loop sends 12 readings 5 seconds apart, so the timer starts at the first and the seventh (30 seconds later) fires the alert: one `ALERT` line about 30 seconds after the loop starts, then silence for the 5 minutes of cooldown, although five more readings are above the limit. Then publish `{"temperature": null}`: the engine must skip it and keep running. A second alert inside the cooldown, or an engine that stops, means the rule or the code is wrong.

### Core Nodes for IoT Automation

These are the nodes you will use most often.

| Node | Category | Purpose |
|------|----------|---------|
| **mqtt in** | Network | Subscribe to an MQTT topic and receive messages |
| **mqtt out** | Network | Publish a message to an MQTT topic |
| **function** | Function | Write JavaScript to transform or evaluate data |

### Building a Complete Automation Flow

The flow has this shape: one input, one test, and three outputs.

```text
  ┌──────────┐   ┌──────────┐   ┌─────────┐
  │ MQTT In  │──►│ Function │──►│ Switch  │
  │ (sensor/ │   │ (parse   │   │ (temp   │
  │  temp)   │   │  JSON)   │   │  > 35?) │
  └──────────┘   └──────────┘   └────┬────┘
                                     │
                          ┌──────────┼──────────┐
                          ▼          ▼          ▼
                     ┌────────┐ ┌────────┐ ┌───────┐
                     │ Slack  │ │ Email  │ │ MQTT  │
                     │ notify │ │ alert  │ │ Out   │
                     └────────┘ └────────┘ │(actua-│
                                           │ tor)  │
                                           └───────┘
```

The flow you build does the following:

1. Subscribes to `sensors/greenhouse/temperature`
2. Parses the JSON payload
3. Checks if temperature exceeds 35 C
4. If exceeded: sends a Slack notification AND publishes an MQTT command to turn on a ventilation fan
5. If normal: publishes an MQTT command to turn the fan off

:::caution[The fan must not depend on this flow]
A message from a server can be late, and when the network or the Node-RED computer stops, no command arrives. So the fan controller keeps its own thermostat and limits in its firmware and works with no network. A rule on a server is for what one device cannot know (another device's reading, a person's decision), for oversight, alerts and records.

A `fan_on` that was published is not a fan that turns. Let the controller report its state, and alert when the report does not come. Never let a rule restart a machine that people may be working on, or reopen a gas valve. Those need a person at the place.
:::

#### Step 1: MQTT Input Node

Drag an **mqtt in** node onto the canvas and configure it:

| Property | Value |
|----------|-------|
| Server | `localhost:1883` (add credentials in the server config) |
| Topic | `sensors/greenhouse/temperature` |
| QoS | 1 |
| Output | parsed JSON object |

#### Step 2: Function Node (Parse and Evaluate)

Connect a **function** node after the mqtt-in node. This node extracts the temperature and adds a flag indicating whether the threshold is exceeded.

```javascript title="Function node: Evaluate Threshold"
// Extract temperature from the incoming MQTT payload
var temp = msg.payload.temperature;

if (temp === undefined || temp === null) {
    node.warn("No temperature field in payload");
    return null;  // Drop the message
}

// Attach the raw value and evaluation result
msg.temperature = temp;
msg.threshold = 35;
msg.exceeded = (temp > 35);

return msg;
```

Then add a **filter** node (named rbe in older versions) set to "block unless value changes" on the property `msg.exceeded`. Without it, every reading above 35 sends a Slack message, one every 10 seconds through a hot afternoon, which is the alert people learn to ignore, and every reading below 35 sends one more `fan_off`. With it, each crossing of the limit sends one message and one command. For a value that hovers at 35, add the hysteresis of the automation patterns below.

#### Step 3: Switch Node (Route by Condition)

Connect a **switch** node after the function node. Configure it to route on the property `msg.exceeded`:

| Output | Condition |
|--------|-----------|
| Output 1 | `msg.exceeded` is true |
| Output 2 | `msg.exceeded` is false |

Output 1 is the alert path and output 2 the normal path.

#### Step 4: Alert Path (Slack + Fan ON)

From **Output 1** of the switch node, wire two parallel paths:

**Path A: Slack Notification**

Add a **function** node to format the Slack message:

```javascript title="Function node: Format Slack Payload"
msg.payload = {
    "text": "🔴 *Greenhouse Alert*: Temperature is " +
            msg.temperature + "°C (threshold: 35°C). " +
            "Fan has been activated."
};
msg.headers = { "Content-Type": "application/json" };
msg.url = "https://hooks.slack.com/services/YOUR/WEBHOOK/URL";
return msg;
```

Connect this to an **http request** node set to POST.

**Path B: Fan ON Command**

Add a **change** node that sets `msg.payload` to `{"command": "fan_on", "speed": 100}`, then connect it to an **mqtt out** node publishing to `actuators/greenhouse/fan`.

#### Step 5: Normal Path (Fan OFF)

From **Output 2** of the switch node, add a **change** node that sets `msg.payload` to `{"command": "fan_off"}`, then connect it to another **mqtt out** node publishing to `actuators/greenhouse/fan`.

#### Step 6: Debug Nodes

Add a **debug** node to the output of each path, so that you can see the messages in the Node-RED debug sidebar.

## Automation Patterns

<InArticleAd />


A plain limit sends false alerts in some common cases. These patterns remove them.

### Hysteresis (Preventing Flapping)

A reading that stays close to the limit crosses it again and again, and each crossing sends a message. Hysteresis uses two limits: a higher one to start the alert and a lower one to clear it. A room thermostat works the same way: it starts the heater a little below the set temperature and stops it a little above, or the heater would switch on and off every few seconds.

```python title="hysteresis_example.py"
class HysteresisAlert:
    """
    Alert with separate trigger and reset thresholds.
    Trigger at 35 C, clear at 33 C. This prevents flapping
    when the temperature oscillates around 35 C.
    """

    def __init__(self, trigger_threshold, reset_threshold):
        self.trigger_threshold = trigger_threshold
        self.reset_threshold = reset_threshold
        self.is_active = False

    def evaluate(self, value):
        if not self.is_active and value > self.trigger_threshold:
            self.is_active = True
            return "TRIGGERED"
        elif self.is_active and value < self.reset_threshold:
            self.is_active = False
            return "CLEARED"
        return "NO_CHANGE"

# Example usage
alert = HysteresisAlert(trigger_threshold=35.0, reset_threshold=33.0)

readings = [33, 34, 35.1, 35.5, 34.8, 35.2, 33.5, 32.9, 33.1]
for r in readings:
    result = alert.evaluate(r)
    if result != "NO_CHANGE":
        print(f"  Temp={r}C -> {result}")
```

Output:
```
  Temp=35.1C -> TRIGGERED
  Temp=32.9C -> CLEARED
```

Without hysteresis, the values 35.1, 34.8, 35.2 would start, clear and start the alert again. With it, the alert starts once at 35.1 and clears only below 33 C.

### Dead-Band

A dead-band is a zone around the target value where nothing acts. A heating and cooling system turns the heater on below 20 C and the cooler on above 25 C, and between 20 and 25 neither runs. In a real system this logic runs in the firmware of the controller. It is shown in Python here to make the idea clear.

```python title="dead_band_example.py"
class DeadBandController:
    """
    Dead-band controller for HVAC-style automation.
    Heater ON below low_threshold, cooler ON above high_threshold,
    both OFF in the dead band between them.
    """

    def __init__(self, low_threshold, high_threshold):
        self.low = low_threshold
        self.high = high_threshold
        self.state = "idle"  # "heating", "cooling", or "idle"

    def evaluate(self, value):
        if value < self.low:
            new_state = "heating"
        elif value > self.high:
            new_state = "cooling"
        else:
            new_state = "idle"  # Dead band: neither heater nor cooler runs

        changed = (new_state != self.state)
        self.state = new_state
        return self.state, changed
```

### Scheduled Actions

Some automations are time-based, not data-based. Node-RED's **inject** node can be configured with a cron expression to trigger flows on a schedule. Common examples:

| Schedule | Use Case |
|----------|----------|
| Every day at 06:00 | Turn on greenhouse irrigation |
| Every 15 minutes | Request a status report from all devices |
| Monday 09:00 | Generate and email a weekly sensor summary |
| Sunset (calculated) | Turn on outdoor lights |

In Python, use the `schedule` library or system cron jobs. Notice that the irrigation command carries its duration: the device must close the valve by itself after 30 minutes, because the message that would stop it may never arrive.

```python title="scheduled_action.py"
import schedule
import time
import paho.mqtt.client as mqtt

client = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2)
client.connect("localhost", 1883)
client.loop_start()  # Background thread keeps the connection alive between jobs

def morning_irrigation():
    """Turn on the irrigation system every morning."""
    client.publish(
        "actuators/greenhouse/irrigation",
        '{"command": "start", "duration_minutes": 30}',
        qos=1
    )
    print("Irrigation started (30 min)")

def request_status():
    """Ask all devices to report their status."""
    client.publish(
        "commands/all/status",
        '{"request": "report"}',
        qos=1
    )

# Schedule tasks
schedule.every().day.at("06:00").do(morning_irrigation)
schedule.every(15).minutes.do(request_status)

while True:
    schedule.run_pending()
    time.sleep(1)
```

### If-Then Rules in Node-RED

Some conditions need two values at once. A function node expresses them more easily than the visual switch node.

```javascript title="Function node: compound condition"
// Only alert if temperature is high AND humidity is low
// (high temp + low humidity = fire risk in a warehouse)
var temp = msg.payload.temperature;
var humidity = msg.payload.humidity;

if (temp > 40 && humidity < 20) {
    msg.alert = "FIRE_RISK";
    msg.payload = {
        text: "Fire risk: temp=" + temp + "C, humidity=" + humidity + "%"
    };
    return msg;
}

return null;  // Drop message if condition not met
```

## Grafana Alerting

<InArticleAd />


If you already have Grafana dashboards, you can add an alert rule to a panel, so that the rule sits beside the chart it watches.

### Creating a Grafana Alert Rule

<Steps>
1. **Open the panel** you want to alert on (e.g., a temperature time-series chart).

2. **Click the panel title** and select **Edit**.

3. **Go to the Alert tab** and click **Create alert rule from this panel**.

4. **Define the condition.** Select the query (your InfluxDB query for temperature), set the reducer to "last" (or "avg" for smoothing), and set the threshold. For example: "WHEN last() OF query(A) IS ABOVE 35."

5. **Set the evaluation interval.** How often Grafana checks the condition. Every 10 seconds is reasonable for real-time monitoring.

6. **Set the "for" duration.** This is the "sustained_seconds" of the Python engine. With 30 seconds, the condition must stay true for 3 checks at a 10-second interval before the alert fires.

7. **Configure contact points.** Go to **Alerting > Contact Points** in the Grafana sidebar. Add a contact point for each channel (email, Slack webhook, Discord webhook), then assign it to your alert rule.

8. **Save the dashboard.**
</Steps>

### Grafana Alert Limitations

Grafana alerting has limits that you should know.

| Limitation | Impact |
|-----------|--------|
| Tied to dashboard queries | Cannot alert on raw MQTT; data must be in the database first |
| Evaluation interval minimum | 10 seconds (not truly real-time) |
| Limited logic | Simple threshold and range conditions; complex compound rules require recording rules in InfluxDB or a separate engine |
| Notification templates | Less flexible than custom Python formatters |
| Stateful only within Grafana | If Grafana restarts, pending alert states may reset |

For simple "value above X" alerts, Grafana works well. For anything more complex, use the Python engine or Node-RED.
