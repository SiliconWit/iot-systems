Automatic scanners search the internet for brokers that accept anyone, and they find a new one quickly. A stranger can then read every sensor, publish false readings, and send commands to your devices. A password alone does not stop this: on a plain connection the password travels as readable text, and one stolen device can still write to every topic. In this lesson you build a Mosquitto broker on Linux and close each of these doors in turn: passwords, a list of which user may use which topic, and TLS encryption. Then you bridge selected data to a remote broker: a second one you run, or a hosted one. #MQTT #Mosquitto #TLS

## MQTT Fundamentals

<InArticleAd />


Every setting in this lesson acts on five MQTT ideas, so here they are in short. The lesson on [MQTT with the ESP32](/education/embedded-programming-esp32/mqtt-cloud-communication/) teaches them in full.

### The Publish/Subscribe Model

```text
  Publishers              Subscribers
  ──────────   ┌────────┐ ───────────
  ESP32 ──pub──►│        │──sub──► Grafana
  (temp data)  │ MQTT   │
               │ Broker │──sub──► Alert Engine
  Pico W ──pub─►│        │
  (humidity)   │(Mosqu- │──sub──► Mobile App
               │ itto)  │
  STM32 ──pub──►│        │──sub──► Data Logger
  (air qual)   └────────┘

  Devices never talk directly to each other.
  The broker routes messages by topic match.
```

The broker is the central server that passes messages on. A **publisher** sends a message to a **topic** on the broker. A **subscriber** tells the broker which topics it wants. The broker gives each message to every client whose subscription matches. It works like a sorting office that copies each letter into every mail box whose owner asked for that address. The comparison stops at storage: a post office keeps letters until they are collected, while a broker keeps nothing except a retained message or the queue of a persistent session.

The sensor does not know whether zero, one or fifty clients are listening. That is why the broker is the place to control access: every message passes through it.

A topic is a name with levels, separated by forward slashes:

```
sensors/greenhouse/temperature
sensors/greenhouse/humidity
sensors/rooftop/wind_speed
actuators/greenhouse/ventilation
```

Subscribers can use two wildcards:

- **`+`** matches exactly one level: `sensors/+/temperature` matches `sensors/greenhouse/temperature` and `sensors/rooftop/temperature` but not `sensors/greenhouse/zone1/temperature`.
- **`#`** matches all remaining levels: `sensors/#` matches every topic that starts with `sensors/`.

:::caution[Never subscribe to `#` in production]
Subscribing to `#` receives every message on the entire broker. This is useful for debugging but creates unnecessary load and potential security issues in production.
:::

### Quality of Service (QoS) Levels

The quality of service (QoS) level says how hard the sender tries to hand a message to the broker. A higher level costs more packets.

<CardGrid>
  <Card title="QoS 0: At Most Once" icon="star">
    The publisher sends the message once and gets no confirmation. It may arrive or it may be lost. Use it for frequent readings, where the next one replaces a lost one. One packet: PUBLISH.
  </Card>

  <Card title="QoS 1: At Least Once" icon="approve-check">
    The publisher waits for a confirmation packet (PUBACK) from the broker and sends the message again if none comes. The broker receives it at least once, and sometimes twice. This is a good default. Two packets.
  </Card>

  <Card title="QoS 2: Exactly Once" icon="warning">
    Four packets (PUBLISH, PUBREC, PUBREL, PUBCOMP) make sure the broker receives the message once and only once. Use it where a repeat would do harm, such as a billing record. Four packets per message.
  </Card>
</CardGrid>

Every level describes one step only: from a sender to the broker, or from the broker to one subscriber. A PUBACK tells the device that the broker has the message. It does not tell the device that any subscriber received it or that a person saw it.

For that reason an alarm must never depend on MQTT alone. The device sounds its own alarm and applies its own limits first. The message is the report of what happened.

### Retained Messages

A broker normally keeps no copy of a message. When a publisher sets the **retain** flag, the broker stores that message as the last one for the topic and gives it to every new subscriber at once, even days later.

This suits status topics. If a sensor publishes `"online"` to `devices/sensor01/status` with retain=true, a client that subscribes later knows the state at once.

To clear a retained message, publish an empty payload (zero bytes) to the same topic with retain=true.

### Last Will and Testament (LWT)

A device that loses power cannot say goodbye. So when a client connects, it can leave a "last will" with the broker: a message for the broker to publish if the client disappears without a proper disconnect (network failure, crash, power loss). The broker notices the silence only after 1.5 times the keepalive time, the agreed longest pause between packets.

This is the standard way to detect offline devices:

<Steps>
1. On connect, the client registers LWT: topic `devices/sensor01/status`, payload `"offline"`, retain=true.

2. After connecting, the client publishes `"online"` to `devices/sensor01/status` with retain=true.

3. If the client disconnects gracefully, it publishes `"offline"` to the status topic before disconnecting.

4. If the client disconnects unexpectedly, the broker publishes the LWT `"offline"` message automatically.
</Steps>

Either way, subscribers see the right status, with a delay of up to 1.5 times the keepalive after a power loss.

### Clean Session vs. Persistent Session

With **clean session = true** (the default), the broker forgets a client when it disconnects. Its subscriptions are gone, and messages published while it is away are not kept for it.

With **clean session = false**, the broker remembers the client's subscriptions and queues the QoS 1 and QoS 2 messages that arrive while the client is offline. When the client returns with the same client ID, it receives the queued messages. This requires:

- A stable, unique **client ID** so the broker can identify the returning client.
- QoS 1 or QoS 2 on the subscription. QoS 0 messages are never queued.

The queue has a limit (`max_queued_messages` in the configuration below). Messages over the limit are dropped. A persistent session suits a battery device that sleeps for minutes or hours between connections.

:::note[MQTT 5.0 replaces "clean session" with "clean start" and "session expiry interval"]
MQTT 5.0 separates the concepts: `clean_start` controls whether to resume a session, and `session_expiry_interval` controls how long the broker keeps the session after disconnect. Mosquitto 2.x supports both MQTT 3.1.1 and 5.0.
:::

<InArticleAd />


Mosquitto is the most widely used open-source MQTT broker. It is small enough to run on a Raspberry Pi beside other services.

## Basic Mosquitto Configuration

<InArticleAd />


Start with a first configuration that does three things: it opens a listener (a port on which the broker accepts connections), it refuses clients that give no username, and it turns on persistence, which means the broker saves retained messages and sessions to disk so they survive a restart.

```conf title="/etc/mosquitto/conf.d/default.conf"
# ── Listener ──
listener 1883
protocol mqtt

# ── Authentication ──
allow_anonymous false
password_file /etc/mosquitto/passwd

# ── Persistence ──
persistence true
# The Debian, Ubuntu and Raspberry Pi OS main file already sets
# persistence_location and "log_dest file". A second value stops
# Mosquitto ("Duplicate ... value"), so remove the # below only if
# your mosquitto.conf does not set them.
# persistence_location /var/lib/mosquitto/
autosave_interval 300

# ── Limits ──
max_connections 100
max_inflight_messages 20
max_queued_messages 1000
message_size_limit 262144

# ── Logging ──
# log_dest file /var/log/mosquitto/mosquitto.log
log_type error
log_type warning
log_type notice
log_type information
connection_messages true
log_timestamp true
log_timestamp_format %Y-%m-%dT%H:%M:%S
```

Read the main file first (`grep -v '^#' /etc/mosquitto/mosquitto.conf`): Mosquitto refuses to start when a one-value setting such as `persistence_location` appears twice, and says why in `sudo journalctl -u mosquitto -n 20`, not in its log file.

**Key directives explained:**

| Directive | Purpose |
|-----------|---------|
| `listener 1883` | Open a listener on TCP port 1883 |
| `allow_anonymous false` | Require username/password for all connections |
| `password_file` | Path to the password file created by `mosquitto_passwd` |
| `persistence true` | Store retained messages and subscriptions to disk |
| `autosave_interval 300` | Write the persistence database every 300 seconds |
| `max_connections 100` | Limit total simultaneous connections |
| `max_queued_messages 1000` | Maximum queued messages per client (persistent sessions) |
| `message_size_limit 262144` | Maximum message payload size in bytes (256 KB) |

After saving the config, restart Mosquitto:

```bash title="Restart Mosquitto with new config"
sudo systemctl restart mosquitto
sudo systemctl status mosquitto
```

If the service fails to start, check the log (and the journal, as above, for a mistake in the configuration):

```bash title="View Mosquitto log for errors"
sudo tail -50 /var/log/mosquitto/mosquitto.log
```

## Password Authentication

<InArticleAd />


Mosquitto keeps its users in a password file, managed with the `mosquitto_passwd` tool. The file does not hold the passwords themselves. It holds a hash of each one, a scrambled form that cannot be turned back into the password.

<Steps>
1. Create the password file and add the first user:

   ```bash title="Create password file with first user"
   sudo mosquitto_passwd -c /etc/mosquitto/passwd sensor_node_01
   ```

   You will be prompted to enter and confirm a password. The `-c` flag creates a new file (overwriting any existing one).

2. Add additional users without the `-c` flag (which would overwrite the file):

   ```bash title="Add more users"
   sudo mosquitto_passwd /etc/mosquitto/passwd dashboard_user
   sudo mosquitto_passwd /etc/mosquitto/passwd admin_user
   ```

3. To add a user non-interactively (useful for scripts), use the `-b` flag:

   ```bash title="Add user non-interactively"
   sudo mosquitto_passwd -b /etc/mosquitto/passwd actuator_node_01 MySecurePassword123
   ```

4. To delete a user:

   ```bash title="Delete a user"
   sudo mosquitto_passwd -D /etc/mosquitto/passwd old_user
   ```

5. Verify the password file exists and has the correct ownership:

   ```bash title="Check password file permissions"
   ls -la /etc/mosquitto/passwd
   sudo chown mosquitto:mosquitto /etc/mosquitto/passwd
   sudo chmod 600 /etc/mosquitto/passwd
   ```

6. Restart Mosquitto to pick up the new password file:

   ```bash title="Restart after password changes"
   sudo systemctl restart mosquitto
   ```
</Steps>

### Testing Authentication

Test that anonymous access is denied and authenticated access works:

```bash title="Test: anonymous access should fail"
mosquitto_pub -h localhost -t test/hello -m "anonymous message"
# Expected: Connection error, not authorized
```

```bash title="Test: authenticated access should succeed"
mosquitto_pub -h localhost -t test/hello -m "authenticated message" \
  -u sensor_node_01 -P "YourPasswordHere"
```

In a second terminal, subscribe to verify the message arrives:

```bash title="Subscribe with authentication"
mosquitto_sub -h localhost -t test/hello \
  -u dashboard_user -P "YourPasswordHere"
```

## Topic ACLs

<InArticleAd />


A password is like the key to the front door of a building: it decides who comes in. An ACL (access control list) is the set of keys to the rooms inside: it decides what each user may publish and subscribe to. Without an ACL, any user with a valid password can read and write every topic, so one stolen sensor opens the whole broker.

### Creating an ACL File

Each block names a user and lists topics. The words are from the client's side: `write` lets the user publish to the topic, `read` lets the user subscribe to it, and `readwrite` allows both. A topic that is not listed is refused.

```conf title="/etc/mosquitto/acl"
# ── Admin user: full access to everything ──
user admin_user
topic readwrite #

# ── Sensor node 01: publish to its own topics, subscribe to commands ──
user sensor_node_01
topic write sensors/node01/temperature
topic write sensors/node01/humidity
topic write sensors/node01/status
topic read commands/node01/#

# ── Dashboard user: read all sensor data, no publishing ──
user dashboard_user
topic read sensors/#
topic read devices/+/status

# ── Actuator node 01: subscribe to commands, publish status ──
user actuator_node_01
topic read commands/actuator01/#
topic write actuators/actuator01/status
topic write actuators/actuator01/feedback
```

### Pattern Matching with %u and %c

Mosquitto supports two substitution patterns in ACL rules:

- **`%u`** is replaced with the connecting client's username.
- **`%c`** is replaced with the connecting client's client ID.

This lets you write generic rules that apply to many users:

```conf title="Pattern-based ACL rules"
# Every user can publish to their own sensor topic
pattern write sensors/%u/+

# Every user can read commands addressed to them
pattern read commands/%u/#

# Every user can publish their own status
pattern write devices/%u/status

# Every client can publish to a topic named after its client ID
pattern write clients/%c/data
```

With pattern rules, you do not add a new ACL block for every new device. A device with the username `node07` may publish to `sensors/node07/temperature` and to no other device's topics.

### Enabling ACLs

Add the ACL file directive to your Mosquitto configuration:

```conf title="Add to /etc/mosquitto/conf.d/default.conf"
acl_file /etc/mosquitto/acl
```

Set the correct ownership and restart:

```bash title="Apply ACL file"
sudo chown mosquitto:mosquitto /etc/mosquitto/acl
sudo chmod 600 /etc/mosquitto/acl
sudo systemctl restart mosquitto
```

### Testing ACLs

Verify that sensor_node_01 can publish to its allowed topic:

```bash title="Test: allowed publish should succeed"
mosquitto_pub -h localhost -t sensors/node01/temperature -m '{"temp_c": 23.5}' \
  -u sensor_node_01 -P "YourPasswordHere"
```

Verify that sensor_node_01 cannot publish to another node's topic:

```bash title="Test: unauthorized publish should be rejected"
mosquitto_pub -h localhost -t sensors/node02/temperature -m '{"temp_c": 23.5}' \
  -u sensor_node_01 -P "YourPasswordHere"
# Expected: publish denied (check mosquitto.log for "denied" message)
```

The command itself may print no error. The broker drops the message without telling the publisher, so the log is the place to look. Here again, published does not mean received.

Verify that dashboard_user can subscribe to sensor data but not publish:

```bash title="Test: dashboard read-only access"
# This should work (reading sensors):
mosquitto_sub -h localhost -t "sensors/#" \
  -u dashboard_user -P "YourPasswordHere"

# This should fail (writing to sensors):
mosquitto_pub -h localhost -t sensors/node01/temperature -m '{"temp_c": 99}' \
  -u dashboard_user -P "YourPasswordHere"
```

## TLS Setup with OpenSSL

<InArticleAd />


Plain MQTT on port 1883 sends everything as readable text: usernames, passwords and payloads. Anyone on the same network can copy them. TLS (Transport Layer Security) encrypts the whole connection, and it also lets the client check that it is talking to your broker and not to an imitation.

That check works like an identity card. The broker shows a **certificate**, a file that states its name and carries a signature. The signature comes from a **certificate authority** (CA), an issuer that the client already trusts. Here you make your own CA. Each client gets a copy of the CA certificate and accepts any broker certificate that the CA signed.

```text
  Client (ESP32)              Broker (Mosquitto)
       │  hello                      │
       ├────────────────────────────►│
       │  server certificate         │
       │◄────────────────────────────┤
   checks the signature              │
   with its copy of ca.crt           │
       │  key exchange               │
       ├────────────────────────────►│
       │  encrypted MQTT traffic     │
       │◄───────────────────────────►│
```

You need three files: the CA certificate, the server certificate, and the server private key, the secret that proves the certificate belongs to this broker.

### Generating Certificates

<Steps>
1. Create a directory for the certificates:

   ```bash title="Create certificate directory"
   sudo mkdir -p /etc/mosquitto/certs
   cd /etc/mosquitto/certs
   ```

2. Generate the Certificate Authority (CA) private key:

   ```bash title="Generate CA key"
   sudo openssl genrsa -out ca.key 2048
   ```

3. Create the CA certificate (valid for 10 years):

   ```bash title="Create CA certificate"
   sudo openssl req -new -x509 -days 3650 -key ca.key -out ca.crt \
     -subj "/C=US/ST=State/L=City/O=MyIoTLab/CN=MQTT CA"
   ```

4. Generate the server private key:

   ```bash title="Generate server key"
   sudo openssl genrsa -out server.key 2048
   ```

5. Create a Certificate Signing Request (CSR) for the server. Replace `your-broker-hostname` with the actual hostname or IP of your broker:

   ```bash title="Create server CSR"
   sudo openssl req -new -key server.key -out server.csr \
     -subj "/C=US/ST=State/L=City/O=MyIoTLab/CN=your-broker-hostname"
   ```

   :::tip[The certificate must name the broker the way clients reach it]
   Clients compare the name they connect to with the names in the certificate's Subject Alternative Name (SAN) field. A browser ignores the Common Name (CN), and an IP address only in the CN fails in Python and Node.js ("IP address mismatch"). Put every name and IP address that clients use in the SAN (next step).
   :::

6. Write the names clients use into a small file, then sign the server certificate with the CA (valid for 1 year):

   ```bash title="Sign server certificate"
   echo "subjectAltName=DNS:your-broker-hostname,IP:192.168.1.50" \
     | sudo tee server.ext
   sudo openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key \
     -CAcreateserial -out server.crt -days 365 -extfile server.ext
   ```

   Check that the names are there: `openssl x509 -in server.crt -noout -text | grep -A1 "Alternative"`.

7. Set proper permissions so Mosquitto can read the files:

   ```bash title="Set certificate permissions"
   sudo chown mosquitto:mosquitto /etc/mosquitto/certs/*
   sudo chmod 600 /etc/mosquitto/certs/ca.key /etc/mosquitto/certs/server.key
   sudo chmod 644 /etc/mosquitto/certs/ca.crt /etc/mosquitto/certs/server.crt
   ```

8. Verify the certificate chain:

   ```bash title="Verify certificate chain"
   openssl verify -CAfile /etc/mosquitto/certs/ca.crt /etc/mosquitto/certs/server.crt
   ```

   You should see `server.crt: OK`.
</Steps>

The resulting files:

| File | Purpose | Keep Secret? |
|------|---------|--------------|
| `ca.key` | CA private key, signs other certificates | Yes, highly sensitive |
| `ca.crt` | CA public certificate, distributed to clients | No, share freely |
| `server.key` | Server private key | Yes, broker only |
| `server.crt` | Server public certificate, presented to clients during TLS handshake | No |
| `server.csr` | Certificate signing request (no longer needed) | Can delete |

### Configuring Mosquitto for TLS

Update your configuration to add a TLS listener on port 8883:

```conf title="/etc/mosquitto/conf.d/default.conf (updated with TLS)"
# ── Plain MQTT listener (disable in production) ──
# listener 1883
# protocol mqtt

# ── TLS MQTT listener ──
listener 8883
protocol mqtt
cafile /etc/mosquitto/certs/ca.crt
certfile /etc/mosquitto/certs/server.crt
keyfile /etc/mosquitto/certs/server.key
tls_version tlsv1.2

# ── Authentication ──
allow_anonymous false
password_file /etc/mosquitto/passwd

# ── ACLs ──
acl_file /etc/mosquitto/acl

# ── Persistence ──
persistence true
# Already set in the Debian main file (see the basic configuration)
# persistence_location /var/lib/mosquitto/
autosave_interval 300

# ── Limits ──
max_connections 100
max_inflight_messages 20
max_queued_messages 1000
message_size_limit 262144

# ── Logging ──
# log_dest file /var/log/mosquitto/mosquitto.log
log_type error
log_type warning
log_type notice
log_type information
connection_messages true
log_timestamp true
log_timestamp_format %Y-%m-%dT%H:%M:%S
```

The plain listener on port 1883 is commented out. In real use, open only the TLS listener.

Restart and verify:

```bash title="Restart Mosquitto with TLS"
sudo systemctl restart mosquitto
sudo systemctl status mosquitto
```

Check the log to confirm TLS is active:

```bash title="Verify TLS listener started"
sudo grep -i "opening" /var/log/mosquitto/mosquitto.log | tail -5
```

You should see a line indicating the listener opened on port 8883.

### Testing TLS Connections

Copy the `ca.crt` file to the machine where you will run the test clients. Then test:

```bash title="Publish over TLS"
mosquitto_pub -h your-broker-hostname -p 8883 \
  --cafile /path/to/ca.crt \
  -u sensor_node_01 -P "YourPasswordHere" \
  -t sensors/node01/temperature -m '{"temp_c": 24.1}'
```

```bash title="Subscribe over TLS"
mosquitto_sub -h your-broker-hostname -p 8883 \
  --cafile /path/to/ca.crt \
  -u dashboard_user -P "YourPasswordHere" \
  -t "sensors/#"
```

If you connect by an IP address that is not in the certificate's SAN, the name check fails. Add the address to `server.ext` and sign again; for a quick test only, `--insecure` skips the name check. Do not use `--insecure` in production.

```bash title="Connect by IP (testing only)"
mosquitto_pub -h 192.168.1.50 -p 8883 \
  --cafile /path/to/ca.crt --insecure \
  -u sensor_node_01 -P "YourPasswordHere" \
  -t sensors/node01/temperature -m '{"temp_c": 24.1}'
```

## Optional: A Hosted Broker (SiliconWit.io)

<InArticleAd />


This section is optional: every later lesson works with the broker you built above. [SiliconWit.io](https://siliconwit.io), our monitoring service, runs a hosted MQTT broker where devices publish telemetry and receive commands, and it keeps the record, the charts and the alerts. When you register a device there, you receive credentials and a topic structure that keeps each device isolated. It works with any MQTT client, so a device moves between it and your own broker when you change the host, the credentials and the topics.

### Connection Details

| Parameter | Value |
|-----------|-------|
| Host | `mqtt.siliconwit.io` |
| Port | 8883 (MQTT over TLS) |
| WebSocket port | 8084 (WSS) |
| Username | Your device ID (from [siliconwit.io](https://siliconwit.io), Dashboard -> Devices) |
| Password | Your access token (from [siliconwit.io](https://siliconwit.io), Dashboard -> Devices) |
| Publish topic | `d/{device_id}/t` (telemetry data) |
| Subscribe topic | `d/{device_id}/c` (commands from the cloud) |
| TLS | Required, uses a publicly trusted CA certificate |

### Testing with Command-Line Tools

```bash title="Publish telemetry to SiliconWit.io"
mosquitto_pub -h mqtt.siliconwit.io -p 8883 \
  --capath /etc/ssl/certs/ \
  -u "YOUR_DEVICE_ID" -P "YOUR_ACCESS_TOKEN" \
  -t "d/YOUR_DEVICE_ID/t" \
  -m '{"temperature": 23.5, "humidity": 61.2}'
```

```bash title="Subscribe to commands from SiliconWit.io"
mosquitto_sub -h mqtt.siliconwit.io -p 8883 \
  --capath /etc/ssl/certs/ \
  -u "YOUR_DEVICE_ID" -P "YOUR_ACCESS_TOKEN" \
  -t "d/YOUR_DEVICE_ID/c"
```

Because `mqtt.siliconwit.io` uses a certificate signed by a public CA (not self-signed), you can use `--capath /etc/ssl/certs/` to point to the system's trusted CA bundle instead of a specific CA file.

### Topic Structure

The SiliconWit.io topic structure follows a simple convention:

```
d/{device_id}/t     Telemetry: device publishes sensor data here
d/{device_id}/c     Commands: device subscribes here for remote commands
d/{device_id}/s     Status: device publishes online/offline status
```

The ACL on the SiliconWit.io broker ensures that each device can only access its own topics. Device A cannot read or write to Device B's topics.

## WebSocket Support

<InArticleAd />


A web page cannot open a plain MQTT connection, because a browser does not let its scripts use raw TCP. A browser can open a WebSocket, a lasting two-way connection that starts as a web request, and MQTT can travel inside it. This is how a web dashboard receives live sensor data. Mosquitto accepts WebSocket listeners beside its normal ones.

### Configuring WebSocket TLS (WSS)

Add a WebSocket listener to your configuration:

```conf title="Add to /etc/mosquitto/conf.d/default.conf"
# ── WebSocket TLS listener ──
listener 8084
protocol websockets
cafile /etc/mosquitto/certs/ca.crt
certfile /etc/mosquitto/certs/server.crt
keyfile /etc/mosquitto/certs/server.key
tls_version tlsv1.2
```

This listener uses the same certificate files as the MQTT TLS listener. Restart Mosquitto:

```bash title="Restart for WebSocket support"
sudo systemctl restart mosquitto
```

### Testing with a Browser Client

You can test WebSocket connectivity using any MQTT.js-based client. A quick test with the `mqtt` npm package:

```javascript title="websocket-test.js"
const mqtt = require("mqtt");

const client = mqtt.connect("wss://your-broker-hostname:8084", {
  ca: require("fs").readFileSync("/path/to/ca.crt"),
  username: "dashboard_user",
  password: "YourPasswordHere",
  rejectUnauthorized: true,
});

client.on("connect", () => {
  console.log("Connected via WebSocket TLS");
  client.subscribe("sensors/#");
});

client.on("message", (topic, message) => {
  console.log(`${topic}: ${message.toString()}`);
});
```

For SiliconWit.io, the WebSocket endpoint is `wss://mqtt.siliconwit.io:8084`. The same device credentials (device ID as username, access token as password) work for both MQTT and WebSocket connections.

## Mosquitto Bridge Configuration

<InArticleAd />


A bridge connects two MQTT brokers so that a message published on one also appears on the other. Your local Mosquitto broker collects data from the sensors on your network and keeps working when the internet fails. The bridge forwards the topics you select to a remote broker for records, charts and alerts.

### Bridge to a Remote Broker

The example below forwards to the optional hosted broker of the previous section. To bridge to a second Mosquitto that you run, change `address`, the credentials and the remote topic names (and give `bridge_cafile` your own `ca.crt`); the rest is the same. Add a bridge configuration to your Mosquitto config:

```conf title="/etc/mosquitto/conf.d/bridge.conf"
# ── Bridge to SiliconWit.io ──
connection siliconwit_bridge
address mqtt.siliconwit.io:8883

# Authentication
remote_username YOUR_DEVICE_ID
remote_password YOUR_ACCESS_TOKEN

# TLS for the bridge connection
bridge_capath /etc/ssl/certs/
bridge_protocol_version mqttv311

# Topic mapping, one exact topic each way.
# With "" as the pattern, the two names are full topic names.
# Local readings of node 01 -> the device's telemetry topic
topic "" out 1 sensors/node01/temperature d/YOUR_DEVICE_ID/t

# The device's command topic -> the local command topic of node 01
topic "" in 1 commands/node01 d/YOUR_DEVICE_ID/c

# Bridge options
cleansession false
start_type automatic
restart_timeout 10
try_private false
notifications true
# Publish the bridge status here only, not on the platform
notifications_local_only true
notification_topic bridge/siliconwit/status
```

**Topic mapping syntax:** `topic <pattern> <direction> <QoS> <local_prefix> <remote_prefix>`

- **`out`**: Forward messages from local broker to remote broker.
- **`in`**: Forward messages from remote broker to local broker.
- **`both`**: Bidirectional forwarding.

In this configuration:
- A local message on `sensors/node01/temperature` is published on the cloud as `d/YOUR_DEVICE_ID/t`.
- A cloud command on `d/YOUR_DEVICE_ID/c` appears locally on `commands/node01`, which node 01 may read by its ACL.

A pattern such as `topic sensors/# out 1 "" d/YOUR_DEVICE_ID/t/` keeps the rest of the local name, so a reading lands on `d/YOUR_DEVICE_ID/t/sensors/node01/temperature`. The platform takes telemetry on `d/<device id>/t`, and a broker that allows each device only its own topics refuses the longer name (a test bridge between two Mosquitto brokers logged "Denied PUBLISH"). The bridge also logs in as one device: send all the readings of node 01 in one JSON message, and give a second node its own device and `connection` block.

With `cleansession false`, the local broker keeps outgoing QoS 1 readings during an outage (up to `max_queued_messages`) and sends them on reconnection; a remote broker that keeps sessions does the same for commands. So a command can arrive late. A SiliconWit.io command carries a `timestamp` and a `timeout` (30 seconds): the device must ignore an older one, or a pump switched on an hour ago starts now.

### Verifying the Bridge

After restarting Mosquitto, check that the bridge connected. Use the broker hostname that is in the server certificate, because `localhost` does not match the certificate name and the TLS check fails:

```bash title="Check bridge status"
mosquitto_sub -h your-broker-hostname -p 8883 \
  --cafile /etc/mosquitto/certs/ca.crt \
  -u admin_user -P "YourPasswordHere" \
  -t "bridge/siliconwit/status"
```

You should see a `1` (connected) message. If the bridge fails to connect, check the Mosquitto log for TLS or authentication errors.

Publish a test message locally and verify it arrives on the cloud:

```bash title="Test bridge forwarding"
mosquitto_pub -h your-broker-hostname -p 8883 \
  --cafile /etc/mosquitto/certs/ca.crt \
  -u sensor_node_01 -P "YourPasswordHere" \
  -t sensors/node01/temperature -m '{"temp_c": 25.0}'
```

Subscribe to the topic on the remote broker (or open the device page on SiliconWit.io) to confirm the telemetry data arrived.

## Monitoring with $SYS Topics

<InArticleAd />


Mosquitto publishes its own statistics on topics that begin with `$SYS/`. You can subscribe to them but not publish to them.

### Key $SYS Topics

| Topic | Description |
|-------|-------------|
| `$SYS/broker/version` | Mosquitto version string |
| `$SYS/broker/uptime` | Broker uptime in seconds |
| `$SYS/broker/clients/connected` | Number of currently connected clients |
| `$SYS/broker/clients/total` | Total clients (connected + disconnected with sessions) |
| `$SYS/broker/messages/received` | Total messages received since startup |
| `$SYS/broker/messages/sent` | Total messages sent since startup |
| `$SYS/broker/messages/stored` | Messages held in the message store (retained messages and messages queued for persistent sessions) |
| `$SYS/broker/bytes/received` | Total bytes received |
| `$SYS/broker/bytes/sent` | Total bytes sent |
| `$SYS/broker/load/messages/received/1min` | Messages received per minute (1-minute average) |
| `$SYS/broker/load/messages/sent/1min` | Messages sent per minute (1-minute average) |
| `$SYS/broker/subscriptions/count` | Total active subscriptions |

### Subscribing to $SYS

```bash title="Monitor all $SYS topics"
mosquitto_sub -h your-broker-hostname -p 8883 \
  --cafile /etc/mosquitto/certs/ca.crt \
  -u admin_user -P "YourPasswordHere" \
  -t '$SYS/#' -v
```

The `-v` flag prints the topic alongside the payload, which is essential when subscribing to a wildcard.

:::note[Quote the $SYS topic in your shell]
Use single quotes around `$SYS/#` to prevent the shell from interpreting `$SYS` as an environment variable.
:::

To monitor just the connected client count in a script:

```bash title="Watch connected clients"
mosquitto_sub -h your-broker-hostname -p 8883 \
  --cafile /etc/mosquitto/certs/ca.crt \
  -u admin_user -P "YourPasswordHere" \
  -t '$SYS/broker/clients/connected' -C 1
```

The `-C 1` flag exits after one message.

## Logging and Debugging

<InArticleAd />


When a client cannot connect or a message does not arrive, the log says why.

### Log Type Settings

Each log type can be turned on separately:

```conf title="Logging options in mosquitto.conf"
log_dest file /var/log/mosquitto/mosquitto.log
log_dest stdout

# Log types (enable the ones you need).
# A comment must be on its own line: Mosquitto does not accept
# a comment after a setting.

# Always enable
log_type error
log_type warning
# Connection/disconnection events
log_type notice
# General information messages
log_type information
# Detailed protocol-level messages (verbose)
log_type debug
# Log all subscribe/unsubscribe actions
log_type subscribe
log_type unsubscribe
```

For production, use `error`, `warning`, `notice`, and `information`. Enable `debug` only when actively troubleshooting, as it generates a large volume of output.

### Common Debugging Scenarios

**Client cannot connect:**

```bash title="Watch for connection errors in real time"
sudo tail -f /var/log/mosquitto/mosquitto.log | grep -i "connect\|error\|denied"
```

Look for messages like:
- `Connection refused: not authorised` (bad username/password)
- `OpenSSL Error` (certificate problem)
- `Socket error` (network/firewall issue)

**Client connects but cannot publish or subscribe:**

ACL denials are logged when `log_type information` or `log_type debug` is enabled. Look for:
- `Denied PUBLISH ... (ACL)` (user lacks write permission on that topic)
- `Denied SUBSCRIBE ... (ACL)` (user lacks read permission on that topic)

**Messages are not arriving at subscribers:**

Check that the publisher and subscriber are using the same topic string (topic matching is case-sensitive). Use `mosquitto_sub -v -t '#'` with an admin account to see all messages flowing through the broker.

### Log Rotation

A log file grows without limit. The `logrotate` tool starts a new file at fixed times and deletes old ones:

```conf title="/etc/logrotate.d/mosquitto"
/var/log/mosquitto/mosquitto.log {
    weekly
    rotate 4
    compress
    missingok
    notifempty
    postrotate
        /bin/kill -HUP $(cat /run/mosquitto/mosquitto.pid 2>/dev/null) 2>/dev/null || true
    endscript
}
```

This rotates the log weekly, keeps 4 compressed copies, and sends a HUP signal to Mosquitto so it reopens the log file.

## Docker Deployment

<InArticleAd />


Docker runs a program in a container, a sealed box that holds the program and everything it needs. With Mosquitto in a container, the whole broker is one folder of files that you can copy to another machine and start with one command.

:::tip[Podman as a Docker alternative]
[Podman](https://podman.io) is an open source (Apache 2.0) container engine that runs without root rights or a background service, which suits a gateway. Most `docker compose` commands here work with `podman-compose`; health checks in `depends_on` and container networking may need small changes, so test with `podman-compose up` first.
:::

### Directory Structure

Create a directory structure for the Docker deployment:

```bash title="Create Mosquitto Docker directory"
mkdir -p ~/mosquitto-docker/{config,data,log,certs}
```

<FileTree>
- ~/mosquitto-docker/
  - config/
    - mosquitto.conf
    - passwd
    - acl
  - certs/
    - ca.crt
    - server.crt
    - server.key
  - data/
  - log/
  - docker-compose.yml
</FileTree>

### Configuration for Docker

The configuration is almost identical to the bare-metal setup, but the paths reference the container's filesystem:

```conf title="~/mosquitto-docker/config/mosquitto.conf"
# ── TLS MQTT listener ──
listener 8883
protocol mqtt
cafile /mosquitto/certs/ca.crt
certfile /mosquitto/certs/server.crt
keyfile /mosquitto/certs/server.key
tls_version tlsv1.2

# ── WebSocket TLS listener ──
listener 8084
protocol websockets
cafile /mosquitto/certs/ca.crt
certfile /mosquitto/certs/server.crt
keyfile /mosquitto/certs/server.key
tls_version tlsv1.2

# ── Authentication and ACLs ──
allow_anonymous false
password_file /mosquitto/config/passwd
acl_file /mosquitto/config/acl

# ── Persistence ──
persistence true
persistence_location /mosquitto/data/
autosave_interval 300

# ── Logging ──
log_dest file /mosquitto/log/mosquitto.log
log_dest stdout
log_type error
log_type warning
log_type notice
log_type information
connection_messages true
log_timestamp true
log_timestamp_format %Y-%m-%dT%H:%M:%S
```

### Docker Compose File

The Compose file tells Docker which image to run, which ports to open to the outside, and which host folders appear inside the container.

```yaml title="~/mosquitto-docker/docker-compose.yml"
version: "3.8"

services:
  mosquitto:
    image: eclipse-mosquitto:2
    container_name: mosquitto
    restart: unless-stopped
    ports:
      - "8883:8883"
      - "8084:8084"
    volumes:
      - ./config:/mosquitto/config:ro
      - ./certs:/mosquitto/certs:ro
      - ./data:/mosquitto/data
      - ./log:/mosquitto/log
    user: "1883:1883"
```

### Deploying with Docker

<Steps>
1. Copy your certificates into the `certs/` directory:

   ```bash title="Copy certificates"
   sudo cp /etc/mosquitto/certs/ca.crt ~/mosquitto-docker/certs/
   sudo cp /etc/mosquitto/certs/server.crt ~/mosquitto-docker/certs/
   sudo cp /etc/mosquitto/certs/server.key ~/mosquitto-docker/certs/
   ```

2. Generate the password file inside the Docker container (the format must match the container's Mosquitto version):

   ```bash title="Create password file with Docker"
   docker run --rm -v ~/mosquitto-docker/config:/mosquitto/config \
     eclipse-mosquitto:2 \
     mosquitto_passwd -c /mosquitto/config/passwd sensor_node_01
   ```

   The tool asks for the password, so the container needs a terminal: if it stops with an error instead of a prompt, add `-it` after `docker run`.

   Add additional users the same way (without `-c`):

   ```bash title="Add more users"
   docker run --rm -v ~/mosquitto-docker/config:/mosquitto/config \
     eclipse-mosquitto:2 \
     mosquitto_passwd /mosquitto/config/passwd dashboard_user
   ```

3. Copy your ACL file:

   ```bash title="Copy ACL file"
   sudo cp /etc/mosquitto/acl ~/mosquitto-docker/config/acl
   ```

4. Set ownership so that the container user can read the configuration and certificates and write the data and log directories (UID 1883 is the mosquitto user inside the container):

   ```bash title="Set directory ownership"
   sudo chown -R 1883:1883 ~/mosquitto-docker/config ~/mosquitto-docker/certs \
     ~/mosquitto-docker/data ~/mosquitto-docker/log
   ```

5. Start the container:

   ```bash title="Start Mosquitto in Docker"
   cd ~/mosquitto-docker
   docker compose up -d
   ```

6. Verify it is running:

   ```bash title="Check container status"
   docker compose logs -f mosquitto
   ```

   Press Ctrl+C to exit the log viewer. You should see Mosquitto start up with listeners on ports 8883 and 8084.
</Steps>

### Updating Configuration

When you change the config, password file, or ACL file, restart the container:

```bash title="Restart after config change"
cd ~/mosquitto-docker
docker compose restart
```

To stop and remove the container:

```bash title="Stop Mosquitto container"
cd ~/mosquitto-docker
docker compose down
```

The `data/` and `log/` directories persist on the host, so retained messages and logs survive container restarts.

## Complete Configuration Reference

<InArticleAd />


This is the full configuration, with every part of the lesson in one file. Read it from top to bottom as a list of the doors you closed: two encrypted listeners and no plain one, no anonymous users, the password file, the ACL file, then persistence, limits and logging.

```conf title="/etc/mosquitto/conf.d/default.conf (complete)"
# ============================================================
# Mosquitto production configuration
# ============================================================

# ── TLS MQTT listener (port 8883) ──
listener 8883
protocol mqtt
cafile /etc/mosquitto/certs/ca.crt
certfile /etc/mosquitto/certs/server.crt
keyfile /etc/mosquitto/certs/server.key
tls_version tlsv1.2

# ── WebSocket TLS listener (port 8084) ──
listener 8084
protocol websockets
cafile /etc/mosquitto/certs/ca.crt
certfile /etc/mosquitto/certs/server.crt
keyfile /etc/mosquitto/certs/server.key
tls_version tlsv1.2

# ── Authentication ──
allow_anonymous false
password_file /etc/mosquitto/passwd

# ── Topic ACLs ──
acl_file /etc/mosquitto/acl

# ── Persistence ──
persistence true
# Set once only: the Debian main file already has these two
# persistence_location /var/lib/mosquitto/
autosave_interval 300

# ── Connection limits ──
max_connections 100
max_inflight_messages 20
max_queued_messages 1000
message_size_limit 262144

# ── Keepalive ──
# An MQTT 3.1.1 client that asks for more than 120 s is refused
max_keepalive 120

# ── Logging ──
# log_dest file /var/log/mosquitto/mosquitto.log
log_type error
log_type warning
log_type notice
log_type information
connection_messages true
log_timestamp true
log_timestamp_format %Y-%m-%dT%H:%M:%S
```

### Check it

Try each closed door from a second computer on the network:

1. `mosquitto_pub -h your-broker-hostname -p 1883 -t x -m y` must fail to connect: no plain listener is open.
2. `openssl s_client -connect your-broker-hostname:8883 -CAfile ca.crt -verify_hostname your-broker-hostname` must end with `Verify return code: 0 (ok)`. With a name that is not in the certificate it says `62 (Hostname mismatch)`, which is what an ESP32 would meet.
3. Without `-u` and `-P`, a publish over TLS must print `Connection Refused: not authorised`.
4. `sensor_node_01` publishing to `sensors/node02/temperature` must print nothing, deliver nothing to an admin subscriber on `#`, and add a `Denied PUBLISH` line to the log, even at QoS 1.

A step that succeeds where it should fail is a door still open. Repeat the four checks after every change.

## Exercises

<InArticleAd />


1. **Set up a multi-user broker with ACLs.** Create a Mosquitto broker with four users: `sensor_a`, `sensor_b`, `dashboard`, and `admin`. Configure ACLs so that `sensor_a` can only publish to `sensors/a/#` and subscribe to `commands/a/#`, `sensor_b` can only publish to `sensors/b/#` and subscribe to `commands/b/#`, `dashboard` can read all sensor topics but cannot publish, and `admin` has full read/write access to all topics. Test every permission boundary: verify that `sensor_a` cannot publish to `sensors/b/temperature`, that `dashboard` cannot publish at all, and that `admin` can do everything. Use pattern-based ACL rules with `%u` so a single rule covers both sensors.

2. **Generate certificates and enable TLS.** Follow the OpenSSL steps in this lesson to generate your own CA certificate, server certificate, and server key. Configure Mosquitto to listen on port 8883 with TLS. Test the connection using `mosquitto_pub` and `mosquitto_sub` with the `--cafile` flag. Then intentionally break something (use the wrong CA file, use an expired certificate, use a mismatched hostname) and observe the error messages in both the client output and the Mosquitto log. Document each error and its cause.

3. **Configure a bridge to a remote broker.** Run a second Mosquitto (on another machine, or in Docker on another port) with its own user, or, if you have one, use a device on [siliconwit.io](https://siliconwit.io) and its `d/{device_id}/t` topic. Configure a Mosquitto bridge that forwards one local topic, `sensors/node01/temperature`, to one remote topic. Publish test messages locally and verify with `mosquitto_sub` on the remote broker (or on the device page) that they arrive. Then disconnect your internet connection for 30 seconds while continuing to publish locally. Reconnect and verify that the queued messages arrive at the cloud (this tests `cleansession false` on the bridge). Measure the delay between reconnection and message delivery.

4. **Deploy Mosquitto in Docker with persistence testing.** Set up the Docker deployment described in this lesson. Publish 10 retained messages to different topics. Stop the container with `docker compose down`, then start it again. Subscribe to the retained topics and verify all 10 messages survived the restart (this tests that the persistence volume mount works correctly). Then run a load test: use a bash loop to publish 1000 messages as fast as possible and check `$SYS/broker/messages/received` to confirm all 1000 arrived. Record the messages-per-second rate.

## Summary

<InArticleAd />


- A password decides who may connect. An ACL decides which topics each user may publish and subscribe to. You need both.
- TLS encrypts the connection and lets the client check the broker's certificate. The name in the certificate must match the name the client connects to.
- A QoS level describes one step, to or from the broker. A confirmation from the broker is not proof that a subscriber received the message.
- A bridge forwards selected local topics to a remote platform, and the local broker keeps working without the internet.
- The `$SYS` topics and the log show what the broker does, including the messages it refused.
